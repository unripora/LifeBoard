# 插件编写指南

本文面向想给 LifeBoard 写 JS 插件的人。读完应该能独立写出一个能采集、能登录、出错时知道去哪儿查的插件。

**只用这份指南就能开发，不需要看宿主的源代码。** 宿主提供了哪些能力、各版本分别加了什么，
都写在这份指南和[宿主 API 变更记录](./宿主API变更记录.md)里。遇到这两份文档没覆盖的普通需求，
先按第八章的排查顺序确认是插件问题还是宿主缺口，不要假定一定要改 App。

---

## 一、插件是什么

一个插件是一个 ZIP 包（扩展名 `.jsplugin`），根目录必须有 `manifest.json`：

```
my-plugin.jsplugin
├── manifest.json      必需，必须在根目录
├── main.js            入口脚本
├── client.js          其它模块，可自由拆分
└── util.js
```

模块之间用 ES Module 语法互相引用，路径相对当前文件：

```js
import { parse } from './util.js';
```

**不要用 `require`**，也不要用裸模块名（`import x from 'lodash'`）。运行时只解析包内相对路径，没有 node_modules。

打包方式：把目录压成 ZIP，`manifest.json` 放在最外层（不要在包里再套一层目录），后缀改成 `.jsplugin`。

### 用 TypeScript 写（推荐）

插件可以用 TypeScript 开发，宿主**不需要任何改动**——TS 在构建期被 esbuild 打成一个 `main.js`，
宿主仍然只认 `.js`。类型定义在 [`types/`](./types/)，已逐字段对齐宿主实现。

```bash
npm install            # 首次
npm run typecheck      # 类型检查
npm run build          # 构建产物
npm run package:mihealth
```

关键约束：**`tsconfig.json` 里不要引入 `"DOM"` 或 Node 的 lib/types**。
插件跑在 QuickJS 里，没有 `URL`、`TextEncoder`、`Buffer`、`fetch` 这些全局对象；
让 TS 在它们上报错，正是类型定义的主要价值——它在编译期就挡住「本地能跑、手机崩」。

插件源码里直接引用裸 `ctx`（不需要 import），并在文件顶部加一行引用：

```ts
/// <reference path="../types/index.d.ts" />
```

`mihealth/` 是完整的 TS 示例（4 个模块、约 2700 行）。`_debug/*.mjs` 保持 JS，调试脚本不必进构建链。

#### 自动防线

改插件或改宿主后，跑这两条就能发现大部分「本地能跑、手机崩」的问题：

```bash
cd js-plugins && npm run build          # 类型检查 + 打包 + 产物合规校验
./gradlew :shared:desktopTest           # 真引擎加载 + 类型定义一致性
```

| 防线 | 挡住什么 |
|---|---|
| `npm run typecheck` | 用 `URL` / `Buffer` / `TextEncoder` 等 QuickJS 没有的全局对象；`ctx` 字段名写错 |
| `npm run verify:mihealth` | 产物里有裸模块 import；产物含 Node/浏览器专属 API |
| `MiHealthBundleSmokeTest` | 产物里的语法 QuickJS 不支持；打包后注入的辅助代码用到缺失全局 |
| `JsHostFunctionContractTest` | `ctx.d.ts` 与宿主实际注入的函数集不一致 |

后两条在 `:shared:desktopTest` 里，会读取 `js-plugins/` 下的文件，
所以 `shared/build.gradle.kts` 把 `ctx.d.ts` 和 `main.js` 显式声明成了测试输入——
否则改了这些文件 Gradle 会判定 UP-TO-DATE 而不重跑，测试看着绿、实际没执行。

## 二、manifest.json

```json
{
  "id": "com.example.myplugin",
  "name": "显示名称",
  "version": "1.0.0",
  "versionCode": 1,
  "apiVersion": 1,
  "entry": "main.js",
  "description": "一句话说明这个插件做什么",
  "author": "你的名字",
  "defaultTabName": "所属标签页",

  "metrics": [
    { "metricKey": "STEPS", "bucket": "STEPS", "displayName": "步数" }
  ],

  "credentialSpec": [
    { "name": "account", "displayName": "账号", "required": true, "secret": false },
    { "name": "password", "displayName": "密码", "required": true, "secret": true }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `id` | 全局唯一。用反向域名风格。**同一个 id 只能装一个插件** |
| `versionCode` | 整数，用于判断新旧；升级插件时**必须递增**，否则不会覆盖 |
| `entry` | 入口模块，通常 `main.js` |
| `metrics` | 这个插件产出哪些指标。`metricKey` 是你自己起的名字，之后上报数据时要用 |
| `credentialSpec` | 需要用户填哪些凭据。`secret: true` 会按密码显示（掩码） |
| `pinnedCaSha256` | 可选。要信任的自签 CA 指纹（64 位十六进制，冒号可省略）；或写 `"runtime"` 表示指纹由 `trustCa` 第二参数在运行时提供（分发给多用户时用）。见 [第七章](#七连自签证书的局域网服务) |

`metricKey` 建议用大写加下划线。`bucket` 决定数据的量纲类型，`STEPS` 这类是计数，`SLEEP_MINUTES` 是时长，其余观测类用 `COUNT`。

## 三、插件契约

入口模块按需导出下面这些函数。**除 `fetch` 外都是可选的**：没导出时宿主用安全默认值（比如 `health` 默认健康、`detailUi` 默认无内容），不会报错。

### `export async function fetch(date, ctx)`

采集数据。`date` 是 `YYYY-MM-DD`，`ctx` 见下一节。

```js
export async function fetch(date, ctx) {
    const creds = loadCredentials(ctx);
    const rows = await queryApi(creds, date);
    return rows.map((r) => ({
        metricKey: 'STEPS',
        value: r.steps,
        at: r.timestamp,
    }));
}
```

返回一个数组，每项至少要有 `metricKey` 和 `value`。**裸数组就是「成功」**，空数组表示「今天确实没数据」。

#### 但要区分「没数据」和「没取到」

裸数组表达不了失败。如果你直接 `throw`，宿主只能把它当成一次普通故障，
用户在面板上看到的仍然是「今日无数据」——他会去怀疑手环没戴，而不是网络断了。

所以失败时**返回带 `status` 的对象**，让宿主知道该怎么办：

```js
{ status: 'success',  metrics: [...] }
{ status: 'empty',    reason: '当天没有运动记录' }
{ status: 'temporary', message: '请求超时', retryAfterSeconds: 60 }
{ status: 'authRequired', message: '登录已过期，请重新登录' }
{ status: 'failure',  message: '接口返回结构变了' }
```

| status | 什么时候用 | 宿主怎么处理 |
|---|---|---|
| `success` | 拿到数据 | 正常落库 |
| `empty` | **确定**服务端没有这天的记录 | 不落库，明确显示「无记录」+ 你给的原因 |
| `temporary` | 断网、超时、限流、5xx——过一会可能就好了 | 按 `retryAfterSeconds` 退避，不判定插件坏掉 |
| `authRequired` | 凭据失效 / 被踢下线 | 提示重新登录，**不重试** |
| `failure` | 接口改了、数据格式不符 | 记为不健康并展示原因，不重试 |

三条规则：

1. **「不确定有没有」不能报 `empty`**。超时和解析失败一律 `temporary` 或 `failure`，
   `empty` 只留给「服务端明确告诉你没有」。
2. **`status` 拼错等于 `failure`**，不会当成功。`sucsess` 这种错字会直接暴露出来，
   而不是静默变成「今天没数据」。
3. **`retryAfterSeconds` 优先抄服务端的 `Retry-After`**，自己猜的间隔通常不是太长就是太短。

`authRequired` 值得单独用：它是唯一一种**用户自己动手就能修好**的失败。
混进 `failure` 里，用户只会看到「采集失败」，不知道该点什么。

### `export async function decide(records, ctx)`

对采集到的原始记录做判定与计分。不导出时宿主按默认规则处理。

### `export async function login(inputs)`

多轮登录状态机。**这是最需要设计的地方**，详见第六节。

返回 `LoginResult`：

```js
{ type: 'success' }                                   // 登录成功
{ type: 'needInput', prompt, fields }                 // 还要用户填东西
{ type: 'failure', message }                          // 失败，message 会显示给用户
```

### `export async function authState()`

返回当前登录态：

```js
{ type: 'loggedOut' }
{ type: 'loggedIn', accountName: '138****8888' }
{ type: 'expired', message: '登录已过期' }
```

### `export async function logout()`

清除凭据。要连带清掉自己的会话状态。

### `export async function health()`

返回 `{ status: 'healthy' | 'broken', message }`，用于自检页。

### `export async function detailUi(ctx)`

返回详情页要展示的**节点树**（`UiNode`）。不导出时详情页只显示通用信息。

### `export async function onAction(actionId, ctx)`

用户操作详情页里的交互节点时调用。返回：

```js
{ type: 'noop' }
{ type: 'showMessage', text: '已同步' }
{ type: 'triggerSync' }                          // 让宿主跑一轮完整采集
{ type: 'refreshUi', root: { ...节点树... } }     // 只换插件自己那块内容
```

### 详情页 UI：可组合节点树

`detailUi()` 返回一棵**节点树**，宿主递归渲染。想平铺几个卡片时，返回节点数组即可
（宿主会包成一层不套卡片的 `column`）。

**为什么是树而不是固定的几种区块**：区块只能平铺，写不出「两列并排」「卡片里放
一个列表加一个按钮」「把次要信息折叠起来」。现在组合方式由你用 `children` 表达，
新增插件不需要宿主加类型。

#### 容器

| `type` | 字段 | 说明 |
|--------|------|------|
| `column` | `children`、`spacing`、`card`、`title` | 纵向。`card` 是**唯一**决定套不套卡片的字段，嵌套容器一般写 `false` |
| `row` | `children`、`spacing`、`wrap` | 横向，窄屏自动折行 |
| `collapsible` | `title`、`children`、`collapsed`、`summary` | 可折叠，默认收起 |
| `spacer` | `size` | 纵向留白，档位 `none`/`compact`/`normal`/`loose` |
| `divider` | 无 | 分隔线。卡片内部分组用它，别再套一层卡片 |

#### 内容

| `type` | 字段 |
|--------|------|
| `text` | `title`、`body`、`tone`、`emphasis`（`heading`/`body`/`caption`） |
| `statusCard` | `label`、`value`、`tone`、`detail` |
| `chart` | `title`、`chart`（`kind: line`/`bar`/`progressRing`） |
| `image` | `dataUri`、`aspectRatio` |
| `progress` | `fraction`（0..1）、`label`、`valueText`、`tone` |
| `code` | `code`、`language` |
| `list` | `items`、`dense`、`separator`、`maxHeightDp`、`emptyHint` |
| `table` | `columns`、`rows`（纯文本单元格） |
| `keyValue` | `entries`（`{key, value, tone}`） |

#### 交互

| `type` | 字段 | `onAction` 收到的 value |
|--------|------|------------------------|
| `button` | `label`、`actionId`、`primary`、`enabled`、`payload` | `payload`（未给则空） |
| `input` | `actionId`、`placeholder`、`submitLabel`、`multiline`、`enabled` | 用户输入的文本 |
| `select` | `actionId`、`options`、`multiple`、`submitLabel` | 单选=选中值；多选=JSON 数组文本 |
| `toggle` | `actionId`、`label`、`checked` | `"true"` / `"false"` |

`input` 若声明了 `submitTo`（如 `'session:main'`），输入直接投给数据源，
**不会**进 `onAction`——那是「一次插件调用」，与「往常驻会话里发一句话」是两件事。

#### 媒体（宿主当前降级占位）

`audio` / `video` 可以先写进树里，宿主暂不支持播放时会画一个「此版本暂不支持」的
占位。这样插件不必等宿主发版就能先把界面发出去。

#### `id` 与用户排序

节点都可以带可选的 `id`。它的作用是让用户的排序在插件刷新、重启后还能对上。
**没有 `id` 也能用**，宿主按「类型 + 当前位置」兜底；但位置会随节点增删而变，
条件展示的卡片建议显式给 `id`。

用户的排序规则（插件不需要处理，但要知道）：

- 详情页右上角齿轮 → 「区块顺序」：默认（插件顺序）/ 自定义（拖动调整）。
- 自定义模式下长按拖动；**只有根节点的直接子节点参与排序**，容器内部的节点不参与
  （嵌套排序会让设置项指数膨胀，且你每次调整结构都会让保存的顺序错位）。
- `input`、`select`、`toggle` 是交互节点，**不参与拖动**；你也可以用 `locked: true`
  显式锁住某个节点（例如紧贴图表的说明）。
- 插件升级新增节点时，老节点保持用户顺序，新节点追加到最后。

#### 绑定：把「活数据」交给宿主

有些数据由宿主持续推送（会话消息、连接状态）。自己写轮询或每次重调 `detailUi`
都不对。用 `{ binding: '<source>:<key>:<field>' }` 把它交给宿主托管：

```ts
return {
  type: 'column',
  children: [
    { type: 'list', maxHeightDp: 320, emptyHint: '还没有消息',
      items: { binding: 'session:main:messages' } },
    { type: 'text', emphasis: 'caption', body: { binding: 'session:main:status' } },
    { type: 'input', actionId: 'chat.send', placeholder: '说点什么',
      submitTo: 'session:main',
      enabled: { binding: 'session:main:inputEnabled' } },
  ],
};
```

本期只有一个数据源 `session`，字段三个：`messages` / `status` / `inputEnabled`。
可绑定的字段只有 `list.items`、`text.body`、`statusCard.value`、`input.enabled`——
不支持任意字段绑定（那会滑向表达式语言）。

绑定不可用时（源不存在、key 不存在）该节点**整块不渲染**；绑定到类型不符的字段
则退回空值。插件不需要自己判空。

#### 会话（活数据）怎么接

节点树里出现 `session:*` 绑定时，宿主自动装配并启动会话。插件导出三个函数配合：

```ts
export function sessionStart(config) { /* 建连；成功返回 true */ }
export function sessionEvent(ev) { /* 用户输入：ev.type = 'input'，ev.payload = 文本 */ }
export function sessionStop() { /* 断连；可能被重复调用 */ }
```

`sessionStart` 返回 `false`（或未导出）时，输入框的 `inputEnabled` 会一直是
「不可用」，界面显示「会话未连接」——不要为了让界面好看而假装返回 `true`。

**从插件主动推送**（`ctx.session.emit`）：

```ts
export function sessionStart(config) {
  ctx.session.emit(JSON.stringify({ type: 'status', text: '已连接', inputEnabled: true }));
  return true;
}

// 后台循环里（例如收到服务端消息）
ctx.session.emit(JSON.stringify({ type: 'message', role: 'assistant', text: '任务完成' }));
// 流式片段：会接在当前回复后面
ctx.session.emit(JSON.stringify({ type: 'delta', text: '继续生成中…' }));
```

支持的事件（未知 `type` 会直接报错，便于开发期发现问题）：

| `type` | 字段 | 作用 |
|--------|------|------|
| `message` | `role`（user/assistant/system）、`text` | 追加一条完整消息 |
| `delta` | `text` | 追加到当前回复末尾 |
| `status` | `text`、`inputEnabled` | 更新状态文案与输入可用性 |
| `clear` | 无 | 清空消息（重连后按服务器快照重建） |
| `closed` | `reason` | 插件侧关闭会话 |

注意：`ctx.session.emit` 只在会话期间有效；会话开始前调用会被宿主丢弃。
输入提交走 `sessionEvent`，不要在推消息时重复回显用户内容。

> `ctx.stream.emit`（一次调用过程中的增量）自 v4 起**在详情页不再显示**。
> 它的产物原本落在「最后一个消息列表」上，固定区块删除后这个落点不存在了。
> 函数仍保留以免旧插件报错；需要流式文本请用 `ctx.session.emit` 的 `delta`。

## 四、宿主提供的接口（`ctx.*`）

### 4.1 凭据 `ctx.credentials`

按 `credentialSpec` 里声明的槽位存取。**只有声明过的槽位能用**。

```js
ctx.credentials.get('account');        // 取不到返回 null
ctx.credentials.put('account', value);
ctx.credentials.remove('account');
ctx.credentials.clear();
```

别把临时数据（比如验证码）塞进凭据：凭据是持久化的，会跟着用户走。

### 4.2 日志 `ctx.log`

**这是唯一的日志出口。`console.log` 的输出进不了宿主的日志页，用户排障时看不到。**

```js
ctx.log.d('Tag', '调试细节');
ctx.log.i('Tag', '关键节点');
ctx.log.w('Tag', '可恢复的异常');
ctx.log.e('Tag', '需要用户处理的错误');
```

日志会写进 App 的「自检 → 日志」页，同时镜像到 logcat 的 `LifeBoard` tag。

四条硬约定：

1. **日志失败不能影响业务**。包一层 try/catch，日志是诊断手段，不该成为新的故障源。
2. **不写敏感值**。日志页可以整份导出，密码、令牌、完整账号都不能进日志。账号打码到 `前3***后2` 即可。
3. **URL 只记路径**。很多接口把签名放在 query 上（`_sign`、`token`），整条 URL 写进日志等于泄露凭证。
4. **关键分支都要留一行**。只记异常的日志在正常流程里是空的，出问题时查不到任何线索。

### 4.3 HTTP `ctx.http`

**这是最容易出错的部分，请完整读完本节。**

#### 基本用法

```js
const res = await ctx.http.get('https://api.example.com/data?x=1');
const res = await ctx.http.post(url, body, options);
const res = await ctx.http.request(method, url, body, options);
```

响应结构：

```js
{
  status: 200,                  // HTTP 状态码
  ok: true,                     // 是否 2xx
  body: '...',                  // 文本响应体；二进制响应时为空串
  bodyBase64: null,             // 二进制响应的 base64；文本响应时为 null
  json: {...},                  // 响应体解析成对象，解析失败为 null
  headers: { 'content-type': '...' },   // 键是小写
  setCookie: ['a=1; Path=/', ...]       // 原始 Set-Cookie，多条
}
```

`options` 支持：

| 字段 | 说明 |
|---|---|
| `headers` | 额外请求头，覆盖会话默认头 |
| `userAgent` | 本次请求的 UA |
| `contentType` | body 的 Content-Type，不传按 JSON |
| `followRedirects` | 是否跟随重定向，默认读会话设置 |
| `timeoutMs` | 本次请求超时（毫秒），1 秒～180 秒，不传用默认 |
| `retry` | 是否允许宿主在网络层重试，默认只对 GET/HEAD/OPTIONS 开启 |

**HTTP 错误码不会抛异常**。`404`、`500` 都会正常返回，由你读 `status` 判断。只有网络层失败（超时、DNS、证书）才抛。

#### 超时与重试交给宿主

```js
// 拉一天的历史数据，默认 30 秒不够
await ctx.http.get(url, { timeoutMs: 60000 });

// POST 默认不重试（重复提交可能让服务端执行两次），确认幂等才显式开
await ctx.http.post(url, body, { retry: true });
```

宿主只对**网络层失败**重试。已经拿到响应（含 4xx/5xx）不重试——那属于业务结果，
重发只会把同一份错误再拿一遍。

#### 区分失败原因：`lastError()`

失败时你拿到的是 `Error`，`message` 是 OkHttp 原文。**不要用字符串匹配去猜**
（"timeout" 这种措辞会随 OkHttp 版本变），用宿主给的稳定分类：

```js
try {
    await ctx.http.get(url);
} catch (e) {
    const kind = ctx.http.lastError();   // 'timeout' | 'connect' | 'dns' | 'tls' | 'other'
    if (kind === 'timeout') return { status: 'temporary', message: '请求超时' };
    if (kind === 'dns' || kind === 'connect') {
        return { status: 'temporary', message: '网络不可用' };
    }
    return { status: 'failure', message: String(e) };
}
```

`lastError()` 只记录**最近一次**失败，是瞬时状态。并发请求会互相覆盖，
需要精确归属时请在同一个 `catch` 里立刻读。

#### 表单提交

不要自己拼 `a=1&b=x+y`。表单编码的规则比看上去多（空格是 `+` 不是 `%20`、
`null` 要发空串、同名参数在对象里表达不了），抄错的版本在服务端看来只是「参数错误」。

```js
// 纯编码，不请求
const body = ctx.http.form({ user: 'a', pass: 'p w' });      // user=a&pass=p+w

// 同名参数用二元组数组
ctx.http.form([['tag', 'a'], ['tag', 'b']]);                  // tag=a&tag=b

// 表单 POST：自动带 application/x-www-form-urlencoded
await ctx.http.postForm(url, { user: 'a', pass: 'p w' });
```

`postForm` 的参数既不是对象也不是二元组数组时会**直接报错**，不会静默发一个空表单。

#### 会话：cookie 交给自己管，会出问题

这是踩过的坑，请务必按下面的方式写。

```js
// 建一个会话。同一插件内可以用多个会话（比如多账号）
const session = ctx.http.session('my-session');

// 之后每个请求的 cookie 由宿主自动管理
await ctx.http.get(url, { headers: {...} });
```

**不建会话也能用**：所有请求会落到默认会话，cookie 仍然自动管理。单账号插件通常不需要显式建。

`session` 的名字只在**本插件内**有效。不同插件的会话互不可见，这是隔离要求，不是限制。

#### 会话级设置

```js
ctx.http.setUserAgent(sessionName, 'MyApp/1.0 (Android)');
ctx.http.setHeader(sessionName, 'Referer', 'https://example.com/');
ctx.http.setHeader(sessionName, 'Referer', null);        // 删除
ctx.http.setFollowRedirects(sessionName, true);
```

会话默认头会被单次请求的 `headers` 覆盖。

#### cookie 读写

```js
ctx.http.cookieGet(sessionName, 'token');                  // 取不到返回 null
ctx.http.cookieGet(sessionName, 'token', 'sts.example.com'); // 同名 cookie 按域区分
ctx.http.cookieSet(sessionName, 'deviceId', 'ABC', 'example.com');
ctx.http.cookieSet(sessionName, 'deviceId', 'ABC', '.example.com', '/');  // 带子域
ctx.http.cookieRemove(sessionName, 'token');
ctx.http.cookieClear(sessionName);
ctx.http.cookieAll(sessionName);                           // { name: value, ... }
```

`cookieSet` 主要用在**伪造客户端身份**的场景：服务端要先看到某个 cookie 才认你是官方客户端，而这个 cookie 不是它下发的。这类 cookie 必须自己种。

#### 为什么不能手写 Cookie 头

宿主底层是 OkHttp。**OkHttp 跟随重定向时会重新构造请求，把 `Cookie` 这类逐跳语义的头剔除**，然后交给 CookieJar 重新计算。

如果你手写 `Cookie` 头，而宿主没有 CookieJar（早期版本就是这样），被剔除之后就没人补回来：

- 第一跳正常
- 遇到 302 跳到另一个域，cookie 消失
- 服务端认为这是未认证请求，返回一句含糊的「非法请求」
- **但 HTTP 状态码还是 200**，你完全看不出哪里错了

这个现象极难定位，因为它不报错、不断链，只是行为诡异。所以：

- ✅ cookie 交给会话，不要写 `Cookie` 头
- ✅ 需要伪造身份时用 `cookieSet` 种进会话
- ⚠️ 确实需要手动控制 cookie 的极端场景，才用 `headers: { Cookie: '...' }`，并自己处理重定向

#### 拿只在中间跳下发的凭据

有些服务端把令牌放在重定向链**中间那一跳**的 `Set-Cookie` 里，最后一跳反而是空的。自动跟随会跳过中间响应，你拿不到。

这种场景要关掉自动跟随，逐跳处理：

```js
let current = startUrl;
for (let hop = 0; hop < 10; hop++) {
    const res = await ctx.http.get(current, { followRedirects: false });
    const next = res.headers['location'];
    if (!next) break;
    current = new URL(next, current).toString();
}
// 中间每一跳的 Set-Cookie 都已经进了会话
const token = ctx.http.cookieGet(sessionName, 'token');
```

会话的 CookieJar 在每一跳都会保存，所以逐跳走完直接读就行。

### 4.4 文件 `ctx.files`

插件私有目录，卸载时清空。只能读写相对路径，`..` 会被拦。

```js
ctx.files.read('device_id.txt');       // 不存在返回 null
ctx.files.write('device_id.txt', 'ABC');
ctx.files.list();                      // ['device_id.txt']
```

适合存**设备号**这类需要跨进程稳定的标识。放模块变量是不够的：插件重载（升级、进程重启）后模块状态全丢，你会生成新值，服务端看来就是换了台设备，可能触发风控。

#### 二进制文件要用 Base64 版本

宿主与插件之间只传 JSON 文本，二进制必须用 Base64 表示。
`read` / `write` 走 UTF-8 解码，**用来存图片、protobuf 会损坏数据且不可逆**。

```js
const b64 = ctx.files.readBase64('captcha.png');   // 不存在返回 null
ctx.files.writeBase64('avatar.png', b64);
```

图标、验证码图片、下载的二进制资源都用这一对。

#### 自签证书：`caCertificate` 与 `trustCa`

连局域网里用自建 CA 的服务时，普通请求会 SSL 握手失败。详见 [第七章](#七连自签证书的局域网服务)，两个接口在这里：

```js
const ca = await ctx.http.caCertificate('https://host:port/ca.cer');  // 只接受 https
ctx.http.trustCa(ca);                 // manifest 写死指纹时：与 pinnedCaSha256 比对
ctx.http.trustCa(ca, expectedSha256); // manifest 写 "runtime" 时：第二参数必填
```

装上之后本插件的 `ctx.http.*` 与 `ctx.ws.*` 都只信任这一张 CA。

### 4.5 历史数据与即时上报

```js
ctx.recentMetrics('STEPS', 7);         // [{ date: '2024-01-01', value: 8000 }, ...]
ctx.reportRawRecords('STEPS', records, date);
ctx.reportMetricQueried('STEPS', date);   // 标记「查过但这天没数据」
ctx.report('TURN_DONE', 1);               // 事件型指标：即时累加
```

`recentMetrics` 读的是已落库的数据，不会发网络请求，适合做趋势图。

`ctx.report` 是给**事件型**指标用的：一次对话完成、一次任务失败，都发生在任意时刻，
既不该塞进 `fetch` 的日聚合，也没有别的入口。同一天同一指标多次调用会**累加**
（这正是计数想要的）；`metricKey` 必须在 `manifest.metrics` 里声明过，否则会被丢弃
并记一条宿主告警。它不保证幂等，别在重试循环里调。

### 4.6 其它

```js
ctx.pluginId();                        // 本插件 id
ctx.crypto.md5Hex(bytes);              // 注意参数是 Uint8Array，不是字符串
ctx.crypto.sha1Base64(bytes);
ctx.crypto.sha256Base64(bytes);
ctx.codec.base64Encode(bytes);
ctx.codec.base64Decode(str);           // 返回数组
```

`ctx.crypto.*` 的入参是字节数组。字符串要自己转：

```js
function toUtf8(str) {
    const out = [];
    for (let i = 0; i < str.length; i++) {
        let code = str.charCodeAt(i);
        if (code >= 0xd800 && code <= 0xdbff && i + 1 < str.length) {
            const low = str.charCodeAt(i + 1);
            if (low >= 0xdc00 && low <= 0xdfff) {
                code = 0x10000 + ((code - 0xd800) << 10) + (low - 0xdc00);
                i++;
            }
        }
        if (code < 0x80) out.push(code);
        else if (code < 0x800) out.push(0xc0 | (code >> 6), 0x80 | (code & 0x3f));
        else if (code < 0x10000) out.push(0xe0 | (code >> 12), 0x80 | ((code >> 6) & 0x3f), 0x80 | (code & 0x3f));
        else out.push(0xf0 | (code >> 18), 0x80 | ((code >> 12) & 0x3f), 0x80 | ((code >> 6) & 0x3f), 0x80 | (code & 0x3f));
    }
    return out;
}
```

## 五、运行时限制

| 限制 | 说明 |
|---|---|
| **单线程** | 所有 JS 在插件专用线程上跑，不能开线程 |
| **无 Node API** | 没有 `fetch`、`require`、`process`、`fs`。网络只能用 `ctx.http` |
| **无 DOM** | 不能操作界面，UI 由宿主按你的返回值渲染 |
| **同步调用会阻塞** | 你的 `fetch` 卡住，这个插件的其他调用都会排队 |
| **死循环会被中断** | 宿主有超时打断，但被打断的调用算失败 |

异步能力只有 `Promise` 和 `await`。所有网络请求都是异步的，**必须 `await`**，否则拿到的是 Promise 对象而不是响应。

### 只有 ES 标准库

QuickJS 不是 Node，也没有浏览器那套全局对象。下面这些在桌面 Node 里能用，
插件里**会直接抛 `xxx is not defined`**，而本地测试完全发现不了：

| 不能用 | 替代做法 |
|---|---|
| `new URL()` / `URLSearchParams` | 自己用正则拆 `host` / `path`，见 `util.js` 的 `absoluteUrl` |
| `TextEncoder` / `TextDecoder` | 手写 UTF-8 编码，见 `util.js` 的 `utf8Bytes` |
| `Buffer` | 用字节数组（`number[]`） |
| `atob` / `btoa` | `ctx.codec.base64Encode/base64Decode` |
| `crypto.getRandomValues` | `Math.random()`（nonce 用足够） |

`Map`、`Set`、`Array.from`、`String.prototype.includes` 这些都可用。

**写代码时把这条当成硬约束**：本地桩跑得好好的不代表手机上能跑，
所有"浏览器/Node 顺手就用"的全局对象都要过一遍。

## 六、写登录流程

登录几乎都不是一次调用能完成的：提交密码后服务端可能要求验证码，验证码过了可能还要短信验证。所以 `login` 被设计成**由宿主反复调用**的状态机。

### 基本形状

用模块级变量记住「进行到哪一步」：

```js
let pending = null;    // null 表示没有进行中的登录

export async function login(inputs) {
    const form = inputs || {};

    try {
        if (!pending) {
            // 第一轮：要账号密码
            if (!form.account || !form.password) {
                return needPassword();
            }
            return await startLogin(form.account, form.password);
        }

        if (pending.stage === 'captcha') {
            if (!form.captcha) return needCaptcha(pending);
            return await submitCaptcha(form.captcha);
        }
    } catch (e) {
        // 失败必须清掉中间态，否则用户重试时会卡在上一步
        pending = null;
        return { type: 'failure', message: '登录异常：' + (e && e.message) };
    }
}
```

**中间态只能放模块变量**。`ctx` 每次调用可能是新实例，存不住会话对象。

### 必须提供「退回上一步」

宿主会在验证码类界面上显示「重新输入账号」按钮，它的实现是**提交一个完全空的表单**。

你的 `login` 要识别这种情况并退回第一步：

```js
const wantsRestart =
    !form.account && !form.password && !form.captcha && !form.otp;
if (wantsRestart) {
    pending = null;
    return needPassword();
}
```

不处理这个，用户会卡死：短信收不到、验证码看不清时，点「取消」只是关掉对话框，插件里的中间态还在，再点登录又回到同一个界面。

### 清理中间态的所有出口

登录流程的每个结束点都要 `pending = null`：成功、失败、用户取消、超时。漏一个就会让下一次登录复用上一轮的脏状态。

### 处理「期间用户登出」

异步流程里可能有多轮网络往返，期间用户完全可能点了登出。写回凭据前要比对：

```js
let sessionEpoch = 0;                    // 每次 logout 时 ++

export async function logout() {
    sessionEpoch++;
    pending = null;
    ctx.credentials.clear();
}

// 异步流程起步时记下当时的代数
const epoch = sessionEpoch;
// ...若干次 await...
if (epoch !== sessionEpoch) {
    return { type: 'failure', message: '登录已取消' };
}
saveCredentials(creds);
```

### 失败要说清楚原因

`message` 会直接显示给用户。不要写「登录失败」，要写「验证码已过期，请重新获取」这种能指导下一步动作的话。

## 七、连自签证书的局域网服务

局域网里的服务（电脑上的 DSH 移动网关、路由器后台、NAS）通常用**自建 CA** 签发的证书，系统信任库不认识它，`ctx.http` 会直接抛 SSL 握手失败。

### 为什么不能「不校验」

关掉全部 TLS 校验是一种做法，但那样插件能连任何伪造的服务。宿主改成**只信任你声明的那一张 CA**，其余一律拒绝。

### 两种模式：写死指纹 / 运行时取指纹

| 模式 | manifest 写法 | 适用 | 指纹来源 |
|---|---|---|---|
| 写死 | `"pinnedCaSha256": "3f7a9c…"` | 只给自己用、服务端 CA 固定 | 包内常量，**最严格** |
| 运行时 | `"pinnedCaSha256": "runtime"` | 一个包分发给多个用户，每人电脑的 CA 不同 | 由业务代码在 `trustCa` 第二个参数传入 |

写死模式最简单：一次填好，全生命周期只认那一张 CA。但如果插件要发给别人用，对方的服务端会生成**自己的** CA，指纹不可能预先知道——这时用运行时模式，指纹由用户带外提供（例如配对链接里的 `instance=` 段）。

安全强度不降：指纹仍然来自「用户从自己服务端取得、亲眼看过的值」，中间人伪造的证书算不出这个指纹。

### 三步

**第一步：在 manifest 里声明指纹**

```json
{
  "id": "com.example.dsh",
  "pinnedCaSha256": "3f7a9c...（64 位小写十六进制）"
}
```

指纹是 CA 证书 DER 的 SHA-256。取法：

```bash
openssl x509 -inform DER -in ca.cer -outform PEM -out ca.pem
openssl x509 -in ca.pem -fingerprint -sha256 -noout
# SHA256 Fingerprint=3F:7A:9C:...   ← 冒号和大写都可以，宿主会规范化
```

分发给多个用户时改写成哨兵：

```json
{ "pinnedCaSha256": "runtime" }
```

**格式写错会让整包加载失败**，这是故意的：静默退化成「只用系统证书」会让插件以为连上了自签服务，实际每次握手都在别处失败，排查会绕很远。哨兵 `runtime`（大小写不敏感）是唯一被接受的非指纹值。

**第二步：取回证书并装上信任**

```js
// 写死模式：指纹来自 manifest，比对在宿主内部完成
ctx.http.trustCa(caBase64);

// 运行时模式：第二个参数必须给期望指纹，宿主只认它
ctx.http.trustCa(caBase64, expectedSha256);
```

`caCertificate` 这一步**不校验** TLS——此刻 CA 还没被信任，正常校验必然失败。安全性由随后的 `trustCa` 指纹比对兜住：中间人替换的证书过不了那一步。

运行时模式下，指纹通常来自用户粘贴的配对链接：

```js
// https://<host>:<port>/mobile-access/pair#instance=<CA指纹>&token=<配对码>
const instance = readInstanceFromLink(pastedLink); // 64 位十六进制
ctx.http.trustCa(await ctx.http.caCertificate(`${gateway}/mobile-access/ca.cer`), instance);
```

**第三步：正常发请求**

```js
const res = await ctx.http.get('https://192.168.1.10:3443/api/status');
```

装好之后，本插件的 `ctx.http.*` 与 `ctx.ws.*` 都只信任这张 CA，`wss://` 也能连。

### 三条硬约定

| 约定 | 说明 |
|---|---|
| 必须在第一次业务请求**之前**装 | 已建好的会话 client 是派生副本，晚到的 CA 不会回溯生效 |
| 期望指纹只能来自 manifest 或**调用方传入** | 插件不能自己决定信任谁，否则被篡改的插件可以先换证书再声明它；运行时模式下宿主只认 `trustCa` 第二个参数，不会替你猜 |
| `caCertificate` 只接受 `https://` | http 明文取回一张「CA」毫无意义，只会掩盖配置错误 |

### 服务端还要求同源时

部分网关（如 dsh-mobile）校验 `Origin` 与 `Host`，并要求登录态走 Cookie、写请求带 CSRF 头。这些都能用现有接口做到：

```js
const session = ctx.http.session('gw', true);
ctx.http.setHeader(session, 'Origin', gateway);       // 同源 Origin
ctx.http.setHeader(session, 'x-dsh-mobile-csrf', csrf); // 写请求要的 CSRF
ctx.http.cookieSet(session, '__Host-dsh_ma_session', sessionToken, host);
```

`ctx.http.cookieSet` 的 `domain` 传 IP 时要与请求 URL 的 host 完全一致，否则 cookie 不会被带上。

## 八、常见陷阱

### 1. 空 body 的 POST

```js
ctx.http.post(url, '');      // 空 body
ctx.http.post(url, null);    // 也是空 body
```

宿主会给 POST / PUT / PATCH 补一个空 body，产出合法的 `Content-Length: 0`。这是正常的：很多接口把参数放在 query 上，body 留空。

### 2. 响应 200 不代表成功

服务端经常用 200 返回业务错误：

```json
{ "code": 10012, "desc": "非法请求" }
```

**必须检查响应体里的业务码**，不能只看 `status`。短信没发出去、数据没拉到，很多都是这个原因。

### 3. 响应带前缀

有些服务端在 JSON 前面加防劫持前缀（比如 `&&&START&&&`），直接 `JSON.parse` 会失败。解析前先剥掉：

```js
function parseJson(text) {
    const t = String(text || '').trim();
    const clean = t.startsWith('&&&START&&&') ? t.slice('&&&START&&&'.length) : t;
    try { return JSON.parse(clean); } catch (e) { return null; }
}
```

### 4. 二进制内容不能当文本读

图片这类响应，`body` 是空串，内容在 `bodyBase64` 里。用 `body` 会得到空值。

```js
const bytes = ctx.codec.base64Decode(res.bodyBase64);
```

### 4.1 别用宿主给的 `json` 字段解析有前缀的响应

`res.json` 是宿主用**严格** `JSON.parse` 解析出来的，遇到 `&&&START&&&` 这类前缀
**恒为 `null`**。看起来"响应 200 但没有预期字段"时，先怀疑这个：

```js
// 错：前缀响应下 json 永远是 null，_sign 自然拿不到
const j = res.json;

// 对：自己从 body 解析
const j = parseMiapi(res.body);
```

同理，别对"字段缺失"直接下结论说服务端没返回——很可能是自己解析这一步就丢了。

### 4.2 `followRedirects: false` 是"只发一次"，不是"跳一次"

语义是**把 3xx 原样返回给调用方**，由调用方决定下一跳。若实现成"最多跳一次、
用完就抛错"，第一个 302 就会被当成"重定向次数过多"而抛异常——表现是跳转链
在第一跳就断，后续所有 cookie 都收不到，登录显示"缺关键凭据"。

自己跟跳转时记得：

- 每一跳都把 `setCookie` 收进自己的 cookie 表
- 下一跳按 domain / path 重新拼 `Cookie` 头（跨域不会自动带）
- 解析相对 `location` 要用**当前这一跳的真实 URL** 作基准
- 解析出与当前相同的地址就停，否则会打转

### 4.3 字段名看着一样，不代表语义一样

服务端可能返回格式完全相同、含义完全不同的字段。判断依据只能是**实际打接口**，
不能靠"格式对得上"：

```text
ssecurity = "dZzoCnGU+ke587eXWpolyw=="   // 真会话密钥
psecurity = "Qq218KjztVL8nCULl6LUmg=="   // 同样 base64 16 字节，但用了稳定 401
```

遇到这类"疑似等价"的字段，要么按参考实现只用明确的那一个，要么拿它真打一次接口。
**不要**因为格式一致就当别名用——会多一次 401，还会掩盖真正可用的路径。

### 5. 每次请求都要 `await`

```js
const res = ctx.http.get(url);       // 错：res 是 Promise
const res = await ctx.http.get(url); // 对
```

漏 `await` 不会报错，但 `res` 上没有 `status`、`body`，后面全是 `undefined`，表现为「数据是空的」而不是「代码错了」，很难查。

### 6. 设备标识要持久化

如果服务端按设备号认客户端，这个号必须跨重启稳定。放模块变量是不够的：

```js
let cachedDeviceId = '';

function deviceId() {
    if (cachedDeviceId) return cachedDeviceId;
    const saved = ctx.files.read('device_id.txt');
    if (typeof saved === 'string' && saved.trim().length >= 8) {
        cachedDeviceId = saved.trim();
        return cachedDeviceId;
    }
    const chars = 'ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789';
    let out = '';
    for (let i = 0; i < 16; i++) out += chars.charAt(Math.floor(Math.random() * chars.length));
    cachedDeviceId = out;
    ctx.files.write('device_id.txt', out);
    return cachedDeviceId;
}
```

### 7. 日期按本地时区算

`fetch` 收到的 `date` 是本地日期。自己算日期范围时用本地时间，不要用 `toISOString()`（那是 UTC，跨时区会差一天）。

```js
function formatDate(d) {
    const p = (n) => String(n).padStart(2, '0');
    return d.getFullYear() + '-' + p(d.getMonth() + 1) + '-' + p(d.getDate());
}
```

## 九、调试

### 在 App 里看日志

「自检 → 日志」页，按 tag 筛选。插件日志带 `[你的插件id]` 前缀。

### 在电脑上看

```bash
adb logcat -s LifeBoard:*
```

但日志页更可靠：进程被杀、重启后历史仍在。

### 导出来看

日志页有导出按钮，会带上版本号和机型，方便把问题发出去。

### 排查顺序

出问题时按这个顺序看：

1. **有日志吗** — 一条都没有说明请求没发出去，检查是不是在 `fetch` 之前就抛了
2. **请求发了吗** — 找 `GET/POST xxx -> status` 这行
3. **响应体是什么** — 日志里要打出业务码，不能只打状态码
4. **业务码什么意思** — 对照接口文档，别把 200 当成功

### 本地跑：搭一个 Node 桩（强烈建议）

**不要**靠"装到手机上→点登录→导日志"来调试。一轮十几分钟，而且每次改一行都要重新
打包推送，真实短信验证码还会因此反复触发风控。正确做法是在电脑上把插件真实代码跑起来。

#### 桩要提供什么

插件源码里直接引用裸 `ctx`（没有 import），所以桩只要挂到全局：

```js
// _debug/node-ctx.mjs
globalThis.ctx = { log, crypto, codec, files, credentials, http };
```

逐个模块对齐宿主行为，注意这几处**必须**和宿主一致，否则本地能过、手机崩：

| 桩的实现 | 为什么必须一致 |
|---|---|
| `http.get/post` 把 `{status, ok, body, headers, setCookie, json}` 原样回传 | 插件的分支全建立在这些字段上 |
| `json` 字段用**严格** `JSON.parse`（不剥前缀） | 宿主就是这样，带 `&&&START&&&` 的响应它会返回 null |
| 不让 `fetch` 自动跟随重定向（`redirect: 'manual'`） | 宿主也是关掉自动跟随的 |
| **不**用 `Node` 的 `new URL()` 去解析插件传入的地址 | 只是为了桩自己方便，插件里不能用它，见下 |

`crypto` / `codec` 直接用 Node 内置：

```js
md5Hex: (b) => crypto.createHash('md5').update(Buffer.from(b)).digest('hex'),
sha1Base64: (b) => crypto.createHash('sha1').update(Buffer.from(b)).digest('base64'),
sha256Base64: (b) => crypto.createHash('sha256').update(Buffer.from(b)).digest('base64'),
base64Encode: (b) => Buffer.from(b).toString('base64'),
base64Decode: (s) => Array.from(Buffer.from(s, 'base64')),
```

`credentials` 要模拟宿主的**逐 key** 语义（`get` / `put` / `load` / `clear`），
并在 `put` 时落盘到本地 JSON——这样跑通一次后，后续调试直接复用凭据，
**不用再发短信**：

```js
put: (key, value) => {
    const obj = credRaw ? JSON.parse(credRaw) : {};
    obj[key] = value;
    credRaw = JSON.stringify(obj);
    persist(credRaw);          // 写 _debug/cred.json
}
```

#### 跑真实插件代码

```js
// _debug/probe.mjs
import { installContext } from './node-ctx.mjs';
installContext({ credentials: readFileSync('./cred.json', 'utf8') });

const main = await import('../myplugin/main.js');   // 就是发布的那份代码
console.log(await main.authState());
console.log(await main.fetch('2026-11-12'));
```

一轮几秒。改完立刻能验，不用打包、不用碰手机。

#### 需要验证码时：进程挂着等，不要超时

短信验证码的有效期只有一两分钟，`sleep 30` 那种写法必然错过。把验证码从
**文件**读进来，进程一直轮询等待：

```js
async function waitForCode() {
    for (let i = 0; i < 1800; i++) {           // 最多等 30 分钟
        try {
            const v = readFileSync(OTP_FILE, 'utf8').trim();
            if (/^\d{4,8}$/.test(v)) return v;
        } catch (e) { /* 还没写，继续等 */ }
        await new Promise((r) => setTimeout(r, 1000));
    }
}
```

配合方式：脚本发短信 → 挂着等文件 → 人在聊天里发来验证码 → 写进文件 → 脚本继续。
**绝不要**因为等不到就重发，那会直接触发 `20024 用户行为被限制`。

#### 本地能验到哪一步

| 能验证 | 不能验证 |
|---|---|
| 请求发出、跳转链走通 | 服务端是否真的下发了某个字段 |
| Set-Cookie 收下、跨域传递 | 真实账号是否已有数据 |
| 响应解析、签名、解密 | 风控、限流 |
| 凭据缓存与自愈（401 → 续期） | 具体数值统计是否符合业务预期 |

**别把"离线测试通过"说成"功能验证通过"。** 离线只能证明逻辑自洽，
服务端字段名、跳转形态、返回码这些必须真的打一次接口才知道。

#### 顺手发现的问题往往是真问题

桩和宿主的差异本身有价值。本地报 `xxx is not a function` 时先分清：

- 桩没实现 → 补桩（`reportMetricQueried`、`recentMetrics` 这类）
- 宿主真的没有 → 插件必须能容忍，用 `try/catch` 兜住，不能让观测性调用拖垮业务

发布前过一遍：

- [ ] `manifest.json` 在包根目录，`versionCode` 比上次大

- [ ] 已在本地 Node 桩上跑通（含真实接口），不是只做静态检查
- [ ] 检查了响应体里的业务码，不只看 HTTP 状态
- [ ] 登录流程的每个出口都清了中间态
